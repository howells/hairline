# Hairline

An engraved chart library for React (`@howells/hairline`): ninety charts, pixel-snapped hairlines, one ink hero per chart, banknote textures. `README.md` has the design intent.

## Packages

A pnpm workspace of three packages:

| Path | Package | What it is |
| --- | --- | --- |
| `.` | `@howells/hairline` | The library, published to npm. Source in `src/`, built into `lib/`. |
| `site/` | `@howells/hairline-site` | The docs site (blume), served at `/docs`. |
| `worker/` | `@howells/hairline-worker` | A Mastra app on Cloudflare Workers that lists and renders charts over MCP and HTTP. See `worker/AGENTS.md`. |

`site/` and `worker/` import the library through the workspace, so they need `pnpm build:lib` first.

## Commands

```sh
pnpm dev          # gallery, http://localhost:5173
pnpm typecheck
pnpm lint         # @howells/lint; lint:fix to autofix
pnpm test         # builds the library, typechecks tests, runs vitest
pnpm build        # app + docs site (build:lib builds the package)
pnpm e2e          # visual acceptance suite, needs Docker; see acceptance/README.md
pnpm --filter @howells/hairline-worker test   # the Worker's MCP and render tests
```

## How to verify a change

`pnpm typecheck && pnpm lint && pnpm test` for every change; CI runs the same on pull requests. Add `pnpm e2e` when a chart's drawing changes. A change to `worker/` also needs its own test script.

## Conventions

- A chart's Zod schema in `src/schema/<kind>.ts` is the source of its props, its TypeScript types, its JSON Schema (`lib/json-schema/`, written by `scripts/library-schema.ts`) and its docs props table.
- `src/schema/registry.ts` is what agents read: one entry per chart with its jobs, when (not) to use it, data shape, limits and schema. A chart outside the registry is invisible to the docs' llms.txt and to the Worker.
- `src/index.ts`, `src/kit.ts`, `src/maps.ts`, `src/schema.ts` and `src/entries/` are generated by `scripts/library-index.ts`; don't edit them by hand.

## Boundaries

- **Always:** run the checks above before calling a change done; add a changeset (`pnpm changeset`) for a user-visible library change.
- **Ask first:** adding a dependency; changing the `exports` map in `package.json`; deploying the Worker (`pnpm --filter @howells/hairline-worker deploy`).
- **Never:** publish to npm, bump versions or cut a release without Daniel's go-ahead; regenerate `acceptance/baselines/` from macOS (use `pnpm generate:baselines`, which runs in Docker); overwrite others' uncommitted work.

## Releases

Versioning uses changesets. For a user-visible change, run `pnpm changeset` and commit the generated file with the change. Merging to `main` makes `.github/workflows/release.yml` open a "Version packages" PR; merging that publishes to npm with provenance.
