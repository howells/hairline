# Ship Hairline as a publishable, agent-ready chart library

Hairline can take an open lane: no maintained React library we found offers an editorial, print-grade house style as an installable package, and Hairline's engraved textures, single ink hero and direct labels are a real identity. Today it is a 90-chart gallery with a package-shaped hole in it. It is `private: true`, has no licence, tests, CI or tags, and exports no prop types. Only 71 of its charts are exported, and every chart renders an empty `<div>` on the server. The road to "proudly alongside incumbents" runs through Wiredeck's nine requirements, because they are mostly the same work as becoming a real package: publish, render deterministically, expose a settled signal, scope the theme, publish a schema, and make accessibility structural. Wiredeck's belief that items 2, 3, 5 and 6 are decisive and differentiating holds only partly. Server rendering (2) is table stakes that Hairline currently fails. The ready signal (3) and the per-chart schema plus registry (6) are the genuine openings, and the three-input derived theme (5) is a design edge rather than a technical gap. The first-release acceptance test is Wiredeck's own: one Chart slide holding bars, line, area, scatter, slope and dumbbell, in dark and light, exported to PDF through headless Chromium. Item 4, whether strokes and textures scale with the slide, is the owner's taste call, and the options are laid out below.

## The lane is open, but the package is a gallery today

The incumbents split into "default dashboard chart" and "low-level primitives". Recharts leads React by a wide margin at **about 62M weekly npm downloads and 27.7k stars**, and it underlies shadcn charts, Tremor and Evil Charts ([npm API](https://api.npmjs.org/downloads/point/last-week/recharts), [GitHub](https://api.github.com/repos/recharts/recharts)). Download figures for Recharts vary widely between third-party sources, so only the API pull should be trusted, and the count overstates deliberate choice because shadcn is the default path for generated UIs. The copy-paste lane shares one dashboard look of rounded cards and gradients. Rosen Charts, for instance, pitches RSC compatibility and "zero setup" with neon styling ([rosencharts.com](https://rosencharts.com/)). The design-led niche is small but influential: Observable Plot has 5.4k stars and 1.6M weekly downloads ([npm API](https://api.npmjs.org/downloads/point/last-week/@observablehq/plot)), and its pitch is "In a word: defaults" ([Why Plot](https://observablehq.com/plot/why-plot)). Newsroom assets are themes, taxonomies and SaaS tools rather than React packages. The BBC's bbplot is an R theme ([bbc/bbplot](https://rdrr.io/github/bbc/bbplot/)), the FT Visual Vocabulary is a taxonomy with D3 starter templates ([ft-interactive](https://github.com/ft-interactive/visual-vocabulary-templates)), and Datawrapper is a tool. The positioning to test is "the chart desk, as a React package". Patterns and hatching are an accessibility add-on everywhere else, off by default and caveated as potentially confusing ([Highcharts](https://www.highcharts.com/docs/chart-design-and-style/pattern-fills), [ECharts decal](https://echarts.apache.org/handbook/en/best-practices/aria/)). Hairline can invert that, because its ordered texture ladders carry magnitude the way halftone does in print.

The audit shows how far the artefact is from that promise. The 19 board charts, including `Slope` and `TimeLines`, are not exported, and the exported `HairlineLine` takes a single series. The `data ?? demo` fallback appears in about 74 files, which ships demo data into every consumer bundle. About 20 charts hard-code subject copy in their aria labels, such as "Christmas trees cut in 2022 by state", and legacy names like `DailyUsers` now draw temperature and crops. There are 190 non-exported `Props` interfaces against one exported. `HairlineLine([])` throws, `RungBars([])` produces `-Infinity`, and there are about 116 `Math.min/max` or `data[0]` uses against six length checks. The README and `docs/DATA.md` still describe a fictional company. Provenance is a legal blocker: the early versions were rebuilt from screenshots of a PolyForm-Noncommercial project, and a clean-room rule exists in `docs/BRIEF.md` but is not recorded in a form that would defend a public licence (codebase audit, summary of blockers). The audit's inference holds up: a coherent core of 25 to 30 charts could ship now, and the unexported board family is the most reusable part. Breadth is only a selling point if every chart is consistently styled. The copy-paste kits list 49 to 56 components, so a number like "ninety" should wait until it is true.

## Wiredeck's nine requirements become the spine of the roadmap

The distribution item (1) is mostly packaging. `package.json` has `private: true`, version 0.1.0, two JS entry points and two CSS files, and the install is documented as `file:../charts`, which also explains Wiredeck's Vercel build failure ([package.json](file:///Users/danielhowells/Sites/charts/package.json), [README](file:///Users/danielhowells/Sites/charts/README.md)). The build already uses `preserveModules`, so per-chart subpaths are largely a generated `exports` map built from `scripts/library-index.ts`. The package also needs trimming: `lib/` is 4.4 MB including bundled `us-atlas` and `world-atlas` JSON (about 316 KB) used by two charts, and an `npm pack` yields 575 files and 191 sourcemaps. Atlases belong behind a `/maps` subpath. The release recipe is current practice: ESM-only, Changesets v3 (shipped August 2026) and npm trusted publishing with provenance ([InfoQ](https://www.infoq.com/news/2026/09/changesets-v3-release/)). The repository must be public for provenance, and the OIDC publisher can only be configured after a first publish with a short-lived token ([graph-tooling PR 2126](https://github.com/graphprotocol/graph-tooling/pull/2126)). A size-limit test that imports `RungBars` alone and asserts no atlas or `d3-force` should gate CI.

Server rendering (2) is where the claim fails as a market statement. An empirical probe of `renderToString(<RungBars/>)` against the built library returned only an empty `is-hidden` div, because `useMeasure` starts at 0 and `Plot` and `Chart` render children only when `width > 0` ([hooks.ts](file:///Users/danielhowells/Sites/charts/src/charts/hooks.ts), [core.tsx](file:///Users/danielhowells/Sites/charts/src/charts/core.tsx)). No chart has a `width` prop. Everyone else has a fixed-size path: Recharts `initialDimension` ([PR #3596](https://github.com/recharts/recharts/pull/3596)), visx `initialSize` ([visx docs](https://visx.airbnb.tech/docs/responsive)), ECharts string-SVG SSR ([handbook](https://echarts.apache.org/handbook/en/how-to/cross-platform/server/)), Vega `renderer: 'none'` ([Vega usage](https://vega.github.io/vega/usage/)), and Plot with a JSDOM document ([Plot docs](https://github.com/observablehq/plot/blob/main/docs/getting-started.md)). Hairline must therefore catch up first and can then differentiate, because it can emit real hydratable React DOM where ECharts and Vega emit strings. The design is one shared `width`/`height` fixed mode implemented once in `Plot` and `Chart` (73 and 10 consumers), plus an `initialWidth` for responsive charts. Fixed mode must also pin text measurement. `textWidth` currently falls back to an Inter-bucket estimate when fonts are not loaded and measures a hidden SVG element otherwise, so server, first paint and loaded states can lay out differently ([util-a.ts](file:///Users/danielhowells/Sites/charts/src/charts/glance/util-a.ts)). A `fontMetrics: "estimate"` default in fixed mode makes SVG byte-stable across server and headless Chromium, at the cost of Inter-width labels. The effort is low for the prop and medium-to-risky for verifying about 71 charts at arbitrary widths, since the six target charts were only checked at 1440 and 390 px.

Motion and readiness (3) is the clearest place to lead. Entry animation is gated by a one-shot `IntersectionObserver` (threshold 0.2) that toggles `is-hidden`/`is-shown`, and under both motion preferences an unrevealed plot is invisible ([hooks.ts](file:///Users/danielhowells/Sites/charts/src/charts/hooks.ts), [hairline.css](file:///Users/danielhowells/Sites/charts/src/system/hairline.css)). The code reading therefore predicts that off-screen slides in an all-slides print page export blank, but no one has run Chromium against it yet. There is no `animate` prop, replay or ready signal anywhere in `src`. Incumbents handle readiness ad hoc. ECharts `finished` has documented gaps when animation is off ([#14101](https://github.com/apache/echarts/issues/14101), [#17500](https://github.com/apache/echarts/issues/17500)), Chart.js `onComplete` re-fires on tooltip activity ([#8897](https://github.com/chartjs/Chart.js/issues/8897)), Highcharts needs `plotOptions.series.animation` rather than `chart.animation` ([API](https://api.highcharts.com/highcharts/chart.animation)), and exporters invent flags like `window.__renderDone` ([Anvil](https://www.useanvil.com/ask-anvil/pdfs/charts-images-missing-html-to-pdf-output/)). No source we found documents a declarative DOM readiness contract in a chart library, with the caveat that this absence rests on about 25 snippet-level searches. The proposal is `animate: "scroll" | "mount" | "off"`, `data-hl-ready="true"` on the chart root, and an `onReady` callback. In `off` mode and fixed SSR mode the first HTML is already ready, which is the strongest possible guarantee for an exporter that waits on `[data-hl-ready="true"]` and `document.fonts.ready`. A `replayKey` handles Wiredeck's slide-becomes-current case without a remount. The script-driven charts (`BarRace`, `ScatterMorph`) use `useLive` rather than `useReveal` and need their own handling. The settle-time formula in the notes is an estimate from tokens, not a measurement.

Theming (5) is real work with a good payoff. Tokens are unprefixed globals (`--paper`, `--l0..--l6`, `--hero`) on `:root`, `[data-palette]` and `.surface-dark`. The ramp is stored as hand-written hex per palette, not computed, and `--font-sans` lives only in the demo app's CSS ([tokens.css](file:///Users/danielhowells/Sites/charts/src/system/tokens.css), [app.css](file:///Users/danielhowells/Sites/charts/src/system/app.css)). The charts also need the host's Tailwind v4 build to scan the package, and without it there are no fills or text roles. That is a distribution blocker well beyond Wiredeck, since it excludes CSS-modules, Panda, Tailwind v3 and design-system shops. The fix is a precompiled `hairline.css`, `--hl-` prefixed tokens scoped under `.hl-root`, a legacy alias layer for the demo, and a React-free `deriveTheme({paper, ink, hero, font, mode})` that outputs plain custom properties at SSR time. Deriving the ramp from three inputs is what no incumbent offers. shadcn gives five categorical variables ([shadcn](https://ui.shadcn.com/docs/components/chart)), while Hairline's ladder encodes importance, and lightness-ordered tones survive greyscale by construction. Two caveats apply. The lightness curve behind `l0..l6` is undocumented, so `deriveTheme` must be fitted to the existing hex values, and the "contrast rebuilt, not inverted" property in dark mode must survive. A font metrics option is also required, because Wiredeck's face may not be Inter.

The agent contract (6) is the strongest differentiator. Today `data` is optional with a silent demo fallback, formatters are functions that cannot cross the server boundary, dates are `Date` objects, and the "registry" (`GalleryEntry`) is a list of render closures grouped by implementation family (`lupi`, `glance`), not by analytical job ([gallery/registry.ts](file:///Users/danielhowells/Sites/charts/src/gallery/registry.ts)). The field's pattern is to validate generated specs after the fact, because Vega-Lite's official schema is large (an early copy ran to 6,284 lines) and grammar-constrained generation is listed as future work ([VegaChat](https://arxiv.org/html/2601.15385v1)). AntV's MCP chart server uses zod for arguments but renders remotely to an image URL ([antvis](https://github.com/antvis/mcp-server-chart)), and the AI SDK and json-render treat zod schemas as the component contract ([AI SDK](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)). We found no rendering library that ships per-chart schemas with a when-to-use registry. Hairline's charts are small and bespoke, which makes strict, dozen-field schemas feasible where a grammar cannot. The design is one zod 4 schema per chart with `z.toJSONSchema` output ([Zod](https://zod.dev/json-schema)), formatters as serialisable descriptors, ISO-string dates, `.strict()` validation with no demo fallback that returns typed errors an MCP tool can hand back to the agent, and a React-free registry keyed by the FT's job taxonomy (the vocabulary's category count is cited as eight in some sources and nine in others, and the FT's own repo lists nine including flow, so the registry should use nine). The schemas become the semver contract, which is why they should land before the 1.0 label. The notes did not verify that Wiredeck's MCP tooling or the target model provider accepts JSON Schema 2020-12 and strict-mode subsets, so that needs a quick test.

The remaining three requirements are cheaper. Host-owned frame (7) is mostly satisfied, because the basics charts render only `<Plot>` and the gallery supplies the name. The exceptions are the board charts, which use `<Chart>` with a `<figure>`, panel styling and top and bottom slots, and the in-SVG `note`, which should be renamed `unitNote` since it carries unit keys, not source lines. Accessibility (8) is partial: every chart has a required `aria-label` and `<title>`, but no `role="img"`, `<desc>` or table, and `sr-only` appears in two places ([svg.tsx](file:///Users/danielhowells/Sites/charts/src/charts/svg.tsx)). The right model is a summary and an `sr-only` table generated from the same validated spec, in the first SSR HTML, with a visible toggle as opt-in. Highcharts has the richest module (data table, keyboard navigation, sonification) ([docs](https://www.highcharts.com/docs/accessibility/accessibility-module)), and Recharts 3 turned its keyboard layer on by default ([wiki](https://github.com/recharts/recharts/wiki/Recharts-and-accessibility)). Whether Chromium's tagged PDF carries that structure is unverified. Unique ids (9) are largely met: `useSvgId` builds ids from `useId` and `useTextureIds` derives pattern ids from one base, in about 25 files ([texture-ids.ts](file:///Users/danielhowells/Sites/charts/src/charts/texture-ids.ts)). The failure paths are separate React roots, where each root restarts the counter and `identifierPrefix` or an `idPrefix` on the provider is the answer, and any hard-coded `SplitClips` id. The literal-id audit was not finished and the two-instance uniqueness test is vacuous until SSR works, so it follows item 2.

## Slide scale is a taste decision, and the options cost differently

Item 4 asks whether strokes and texture pitches scale with the slide or stay pixel-snapped. It is not a technical default to be settled by the research. Type is a single constant (`--text-tick: 11px`, `--text-figure: 30px`), but layout in at least 54 files assumes 11 to 12 px Inter advances through `sansWidth`, and 59 files hard-code 102 stroke widths with 1 px lines snapped by `crisp(v) = Math.round(v) + 0.5` ([util.ts](file:///Users/danielhowells/Sites/charts/src/charts/util.ts), [axes.ts](file:///Users/danielhowells/Sites/charts/src/charts/axes.ts)). Texture pitches are whole-pixel constants (`cross: 6, dense: 3, hatch: 4, screen: 4`) with diagonals drawn as 1 px staircases ([texture-ids.ts](file:///Users/danielhowells/Sites/charts/src/charts/texture-ids.ts)). A CSS font-size variable alone would break label reservations, so it is not a real option. The precedents scale everything together: Highcharts renders at a source width so text stays proportional and then applies a raster scale ([export module](https://www.highcharts.com/docs/export-module/export-module-overview)), and Datawrapper's zoom and scale enlarge all elements evenly ([Datawrapper](https://www.datawrapper.de/academy/how-to-change-the-size-of-your-visualizations)).

There are four coherent options. In option A, the chart renders at its logical size and Chromium's `deviceScaleFactor` supplies resolution, with no scale API at all. Hairlines and staircases stay crisp at native resolution and the library is untouched, but this answers PNG and PDF export only. A live 1920 px web slide would still show 11 px labels. In option B, a uniform `viewBox` scale renders at a smaller logical width (a 768 px logical width at 2.5x gives about 27.5 px labels) and scales everything. It is the cheapest slide path, one component and no per-chart edits, and it is faithful to the precedents. But hairlines become 2.5 px rules, a 4 px hatch becomes a 10 px coarse woodcut, and `crisp()` offsets land on half device pixels at non-integer scales, so only 2x and 3x are safe. In option C, B plus `vector-effect: non-scaling-stroke` keeps rules at 1 device pixel, which suits a brand called Hairline, while textures still scale, so the engraving coarsens. Option D adds device-pixel textures through `patternTransform="scale(1/k)"` so the pitch is re-derived at the target density. It keeps the identity at every size but is the least certain: it needs a feasibility spike and Safari and Firefox checks, and nobody has measured pattern behaviour at fractional scales in the three engines. An option E that re-tunes typography per chart touches 54 hand-tuned files and is not worth the cost.

The practical way to decide is cheap: render the six Wiredeck charts at 2x under B, C and D and look at them, because the six use hatch, cross-hatch and stipple and will show the difference immediately. The trade-off to weigh is that the engraved texture is the identity and its fineness is exactly what uniform scaling destroys, while option A puts no burden on the library but leaves the live slide unsolved. The notes' own opinion leans towards "composition scales, hairlines stay one device pixel, texture density is re-derived", which is option D, but that is a judgement from reasoning and not from a rendering. It is the owner's call. The release can ship the `scale`/`fit` viewBox mechanism with a strokes policy and call textures "scaled" until the owner decides.

## House rules and editorial practice fit together if layers stay separate

The owner's rules are the gallery shows only charts and their names, and the identity is engraved, one ink hero, FT-editor restraint. The editorial research appears to pull against them. The Datawrapper, Economist and Amanda Cox consensus treats annotation as the editorial core ("the annotation layer is the most important thing we do", per the [EU guide](https://data.europa.eu/apps/data-visualisation-guide/visual-annotations-introduction)), and the docs research wants a page per chart with a props table, a data shape and a "when to use" note. These fit if each is its own layer on its own surface. Documentation belongs on separate routes. Today the gallery's only documentation is the (i) popover and `#/chart/<ID>`, which sit on the same surface as the no-prose grid, and that is the collision. A docs site (Fumadocs if the showcase is Next.js, because it generates TypeScript props tables, or Starlight if standalone) can carry prose freely ([Fumadocs comparison](https://fumadocs.dev/docs/comparisons)), and the grid stays untouched. An annotation layer should be optional, data-coordinate based and serialisable (point note, range, reference line, leader), resolved by the same collision system as labels, and off by default and in the gallery. It would render in the existing type roles so it reads as engraved furniture and not as a bolt-on. The frame (name, source, note, info) should be a host-composed `Frame` component beside the chart, as `finalise_plot()` is for the BBC ([cookbook](https://bbc.github.io/rcookbook/)), and charts should never take `title` or `source` props. Accessibility text, `<desc>` and the `sr-only` table are not visible prose and so do not breach the rule. The one real tension is whether to ship an annotation layer at all in a house style that prohibits prose in charts, and that belongs on the owner's decision list.

The editorial bar also names engineering the aesthetic needs. Datawrapper's rules suggest degrading by rule, never squeezing: no rotated labels, no condensed text, switch chart type, and move text away ([Datawrapper](https://www.datawrapper.de/blog/text-in-data-visualizations)). For Hairline that implies a priority-ordered direct-label system (hero, extremes, then the rest, dropping losers) and a minimum-mark-size rule that falls back from texture to solid when bars get too thin. The notes found no published test of how engraved marks fail at small sizes, so Hairline would be the first to measure it. Keep categorical textures to about five families per chart, since discrimination falls as the set grows ([PubMed](https://pubmed.ncbi.nlm.nih.gov/40793547/)), and test lightness balance because patterns shift perceived tone ([Datawrapper](https://www.datawrapper.de/blog/colorblindness-part2)). On the engineering side, the quality bar is a layered test suite (SVG-string snapshots, Playwright at DPR 1, 2 and 3 with near-zero tolerance for hairlines, fast-check fuzzing over empty, NaN, duplicate and negative data, axe, and a size budget), documented element-count budgets, and an explicit statement that Canvas and WebGL are out of scope, with SVG fine to roughly 1 to 5k elements ([interactive-data-visualization.com](https://www.interactive-data-visualization.com/core-rendering-engines-tradeoffs/svg-vs-canvas-architecture/)). Two untested risks sit under the whole design: whether resvg or Satori render `<pattern>` fills (relevant to PNG, OG and email paths) and whether crisp 1 px strokes hold at fractional DPR in WebKit and Firefox.

A last editorial point concerns how to say no. The Prettier option philosophy is the template: freeze the option surface, close style-option requests without discussion, and make exceptions technical ([Prettier](https://prettier.io/docs/option-philosophy)). A Hairline "philosophy" page listing what is fixed (one hero, no prose in charts, texture ladders), what is configurable (paper, ink, hero, font) and what closes unanswered would avoid the Tremor trap of a look with no exit ([PkgPulse](https://www.pkgpulse.com/guides/recharts-v3-vs-tremor-vs-nivo-react-charting-2026)). With a Linux Foundation survey finding about 25% of incoming PRs to be low-quality AI output ([Help Net Security](https://www.helpnetsecurity.com/2026/10/26/linux-foundation-open-source-ai-slop/)), an issue-first policy is cheap protection. For money, the solo precedent is MIT code plus a one-time paid companion; Motion+ sells polished examples, and Motion's own post says examples drove sales and release announcements did not ([Motion](https://motion.dev/magazine/motion-independence-one-year-in-review)). A pack of finished chart compositions is more defensible than a docs-gated funnel after Tailwind's 2026 layoffs ([DevClass](https://devclass.com/2026/01/08/tailwind-labs-lays-off-75-percent-of-its-engineers-thanks-to-brutal-impact-of-ai/)), though that is reasoning, not a sourced claim.

## Sequenced roadmap, with Wiredeck's six-chart PDF as the first-release gate

The acceptance milestone is concrete. Wiredeck's six `kind`s map to `RungBars`, `HairlineLine`, `HairlineArea`, `PlumbScatter`, a slope chart, and `DumbbellQueue`. The slope chart is the gap: `Slope` in `board/slope.tsx` is not exported (the built library exports 71 names and `"Slope" in m` is false), its props `rows`, `format`, `height`, `labels`, `domain` and `label` are all required, and it renders a framed `<figure>` through `Chart`. It must be promoted into the bare-plot, schema-backed shape that the other five already follow, and `TimeLines` is the same kind of omission for a later multi-series line. The gate: with the six rendered through a fixed-size, `animate="off"` path, scoped dark and light themes, and ready attributes awaited, Wiredeck's Chromium export produces a PDF with all six charts present, no blank slide, no duplicate ids, and identical SVG across two runs. The phases below are ordered so that this gate passes at the end of Phase 1, with Phase 0 clearing legal and hygiene blockers first.

## Decisions the owner must make

The first is the licence and the written provenance of the early rebuild from a non-commercial project, because nothing public happens before it. The second is the slide scale policy (options A to D above), ideally after rendering the six charts side by side. Third, whether Tailwind stays an authoring tool only, with precompiled CSS shipped, or remains a host requirement; the evidence favours precompiling. Fourth, which 25 to 30 charts make the first stable surface, and whether the other charts ship as "experimental". Fifth, whether `Slope` is rewritten as a bare plot or the board frame is split from it. Sixth, whether an annotation layer exists at all under the no-prose house rule, and whether the in-SVG `note` becomes `unitNote`. Seventh, the font stance: Inter-only with an explicit metrics option, or a general width table. Eighth, whether a shadcn-style registry is a distribution channel or a distraction from the npm package. Ninth, the funding model and contribution policy.

## Conclusion

The research changes the shape of the problem. Hairline does not need more charts or a wider catalogue; it needs the ordinary package virtues that its competitors already have (a fixed-size server render, a public version, a stable prop contract), and then two pieces of infrastructure no incumbent was found to document: a declarative ready state and per-chart schemas with a choose-a-chart registry. Wiredeck was right about where the leverage is and wrong about what the competition lacks. Server rendering is a catch-up item, and treating it as a differentiator would be a mistake.

The design identity is also more fragile than the engineering. Anything that scales, exports or squeezes a chart threatens the pixel-snapped hairlines and engraved textures that make it Hairline, and so slide scale and small-mark degradation are brand decisions dressed as technical ones. Untested items remain: no Chromium run, no rendering of the six at scale, no measurement of settle times, tree-shaken sizes or pattern behaviour in other engines. Those experiments cost days, and they should come before the 1.0 label is applied to any prop shape.
